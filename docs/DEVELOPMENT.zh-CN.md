# Pose Party 开发与实现说明

[English overview](../README.md) · [中文介绍](../README.zh-CN.md)

DT2140 姿势模仿小游戏。默认英语，右上角可切换中文并记住选择。核心游戏界面显示目标小人、摄像头、计时和得分，音乐控制可选；姿势名称与库列表不展示。

## 发布到 GitHub

首次发布请按 [GitHub 发布新手指南](../GITHUB-PUBLISHING.md) 操作：使用 GitHub 网页上传，再在 Settings → Pages 选择 GitHub Actions。项目已准备自动测试和发布工作流，支持 GitHub Pages 的项目子路径。无需改用 Vue。

## 启动

需要 Node.js 22.18+ 或 24 LTS：

```sh
cd pose-party
npm install
npm run dev
```

用 Chrome 等桌面浏览器打开终端显示的本地地址，点击 Enable camera／开启摄像头并允许访问。已有依赖时可跳过 `npm install`。支持全屏和提示音开关；首次运行默认英语，此后记住手动选择的语言。

## 内置与本地背景音乐

点击顶部 ♫ 展开小播放器，直接播放、暂停、上一首／下一首、选歌或调整音量，无需登录、外部视频或跳转。收起控制后音乐继续播放，摄像头和目标小人的空间保持不变。默认不自动播放，音乐与游戏提示音分别控制。

三首完整原版纯音乐随项目放在 `public/music/`：Disco Medusae（迪斯科）、Cipher（电子）、Cold Funk（放克律动）。均来自 Kevin MacLeod 的 incompetech.com，按 CC BY 4.0 署名；播放器折叠说明和 `public/music/CREDITS.md` 保留作者、来源、许可和文件校验值。录音文件未裁剪或转码，播放时会调音量、轮播和局末淡出。音乐部分不依赖外网；姿态模型的网络条件见本文末尾。

“添加本地音乐”支持多选 MP3、WAV、OGG、M4A 等浏览器可解码音频，最多添加 20 首，与内置音乐共同组成播放列表。选文件仅创建本机临时地址，不上传、不复制进项目，也不保存到本地存储。重载页面后需重新选择本地文件。清空时释放全部临时地址，若正在播放本地文件则暂停并回到首个内置曲目。只记住音量；日志只记录内置／本地、播放状态及错误类别，不记录文件名、路径或歌曲标识。

选歌时保留当前播放／暂停状态；上一首／下一首会直接开始新歌曲，播放完毕自动轮播。切题不打断音乐，60 秒结束后约 0.9 秒淡出并暂停；停止摄像头、隐藏标签页或打开性能弹窗时暂停。游戏总时间不因音乐暂停而改变，音乐错误也不影响识别与计分。

## 游戏规则

- 摄像头开启后先用三个实际画面预热身体和面部模型，再进入待机，默认小人轻轻晃动。预热不参与准备确认、保持或计分。
- 开局前按肩宽、可见臂长和全部目标姿势估计预留空间。太近或偏侧时提示后退／居中；站位合适且面向屏幕连续一秒后，准备圆环填满，揭晓第一题并开始 60 秒计时。准备阶段不消耗游戏时间。这是站位估计，仍需以实际摄像头取景为准。
- 每个目标累积一秒有效保持即加一分，没有单题反应时限。游戏中不再要求面向屏幕，也不逐题检查准备。
- 明显姿势错误会立即清空本题保持进度；一般抖动或遮挡最多容忍 150ms；只有单纯的肘／腕出画可保留已有保持进度最多 300ms，期间不计入有效保持时间。混合面部、低可见性等失效按较短的 150ms 处理。超过宽限或摄像头停顿则重置本题保持。当前目标保留，总计时继续。
- 通过后立即隐藏旧姿势，默认小人过渡：0.45 秒绿色反馈、0.9 秒准备动画，然后揭晓新目标。
- 20 个姿势随机抽取（14 个手臂姿势、6 个歪头组合），相邻不重复；过渡期间同样消耗总时间。
- 60 秒到期立即结束计分，显示完成数量并关闭摄像头。正在做的未完成姿势不计分；恰好在截止时完成也不计入。
- 游戏总时间不因转头、遮挡、切题或切换标签而暂停，视频停顿时也能到期结束。
- 结果保留到主动点击 Play again／再玩一次；新局需要重新面向屏幕确认，不会自动连续开局。
- Stop／停止会结束当前运行并释放设备，回到待机。

`src/game.ts` 集中定义：准备确认 1000ms、总时间 60000ms、有效保持 1000ms、一般不确定宽限 150ms、纯边界失效宽限 300ms、绿色反馈 450ms、切题过渡 900ms。`roundId` 只在新目标揭晓时变化；追踪恢复或本题重试不会换题。

## 面向屏幕检测

使用 MediaPipe Face Landmarker 的面部变换矩阵估计头部朝向，接受约 35 度以内的整体偏转，并检查脸部大小、肩膀可见性以及面部与身体是否属于同一个画面位置。准备一秒内转开或识别中断会重置圆环。

这是粗略的头部朝向判断，不是眼动追踪，也不判断眼睛具体看向哪里。开局同时检查上肢预留空间，尚未具备双肩数据时提示双肩入镜；不会仅靠检测到脸就让站位过近的玩家开局。相关阈值在 `src/readiness.ts` 的 `FACE_LIMITS` 中，需在实际摄像头、光线和站位距离下试玩校准。准备阶段运行面部与身体模型；普通手臂题只运行身体模型，歪头组合题才重新运行面部模型。

## 布局与判定

桌面摄像头占游戏区域约 71% 宽度，游戏区域使用大部分视口高度；目标小人常驻左侧。全屏可进一步增大画面。窄手机屏幕为上方目标、下方摄像头。视频与骨架均按原始比例完整适配，不裁切或拉伸。

面对摄像头，让肩膀、手肘和手腕完整可见。高置信度关节位于真实画面 0–100% 范围内即可参与识别，取消旧版额外排除最边缘 1% 的规则。画外、低置信度和缺失关节仍不能得分，也不使用旧坐标补成正确姿势。显示框变大或提高分辨率本身无法找回摄像头视野以外的手；后退、居中或调整实体摄像头取景才会改变手是否入镜。画面采用镜像，按目标的屏幕方向模仿。六个新姿势为左右歪头搭配摊手、机器人和反向机器人；橙色头部、眼睛、鼻子和倾斜颈部标明头部要求。普通手臂题的头部不参与评分。

判定将镜像坐标换算成像素，先提取肩线方向，再比较相对肩线的四段手臂角度。头部倾斜由面部两眼外侧关键点的连线方向减去肩线方向，避免将整个人倾斜误算成独立歪头。歪头目标为约 ±24 度，双眼与头部需要可见并大致朝屏幕；不要求眼睛注视特定位置。

`src/matching.ts` 集中实现以下稳定性处理：

- 对有效角度做时间常数 80ms 的轻量平滑，不平滑可见性，不用旧的可见关节代替当前缺失的点。
- 手臂首次匹配容差为 28 度，已匹配时保持容差为 36 度；头部首次为 10 度、保持为 15 度，减少临界值反复跳变。
- 原始手臂误差超过 44 度或头部误差超过 22 度时立即标记明显错误，平滑不能掩盖错误动作。
- 一般 150ms、纯出画 300ms 内的不确定只暂停保持进度；必须累积 1000ms 有效匹配才能通过。反复缺失不能凭时间流逝自动通过。
- 新题、摄像头中断或画面尺寸变化会清空平滑历史。
- 准备期日志只评估站位与面向屏幕，不再把未展示的随机手臂目标作为准备期匹配结果。出画日志增记镜像画面上／下／左／右边缘类别，不记录坐标或图像。

上述数值仍是试玩初值，需要按实际摄像头、站位和不同玩家校准。摄像头骨架中，手臂和眼线各自变绿表示该部分接近目标。身体整体倾斜只是做了判定补偿，尚未作为新动作考核。

## 计算与响应优化

优先使用独立的经典 Web Worker，在后台加载身体和面部模型。页面只负责摄像头显示、目标、骨架和游戏计时。歪头题两个模型分析同一个捕获画面，再一次性返回结果，避免用不同时间的头部和身体数据拼接判断。

每次最多处理一帧，忙碌时跳过新帧，不排队；ImageBitmap 只在本机页面与 Worker 之间转移，处理后释放。切题、重开、隐藏页面或结束时，旧请求不会再参与计分。超过 250ms 的结果作为过期结果丢弃并重置保持进度，总计时继续。

Worker 或 OffscreenCanvas 不可用时会回退到页面线程；回退路径在身体与面部模型之间让页面有机会刷新，仍使用同一张画面。报告会明确标记 `worker` 或 `main-fallback`，并记录 GPU／CPU 实际选择。

`npm run dev` 和 `npm run build` 会先将锁定版本的官方 MediaPipe CJS 与 WASM 从已安装依赖复制到 `public/mediapipe/`。这是自动生成的目录，不需要手动修改；Worker 使用经典脚本以兼容该版本的 WASM importScripts 加载方式。无需增加依赖。

新增启动预热、异步传输和结果丢弃记录，不代表模型 API 本身一定更快。对比新旧报告时，优先看页面刷新间隔、主线程长任务和端到端延迟；模型本身的耗时可能接近旧值。真正的改进幅度仍需用同一摄像头和站位重新试玩验证。

## 性能记录

页面右下角的 Performance／性能记录可打开报告；游戏结束或手动停止后查看最方便。记录会自动跟随每次开启摄像头开始，包括加载、准备、普通手臂题、歪头题和切题阶段。表情输出仍未开启。

报告包含：

- 显示刷新率、视频呈现帧率和识别频率，三种计数分开，避免把低识别频率直接当作画面卡顿。
- 身体／面部模型 API、匹配、骨架绘制、识别循环及界面脚本更新的耗时；摘要显示平均值、P95 和最大值。
- 普通题与歪头题独立比较；面部模型没有调用时记录为空值，不填成零毫秒。
- 模型加载、三个画面的预热耗时、GPU／CPU 实际选择与回退、计算线程、摄像头分辨率和配置帧率。
- 可见页面中超过或等于 100ms 的刷新间隔、浏览器长任务（若支持）、对应姿势编号与相对运行时间。
- 按秒和按阶段的汇总，以及带时间戳的逐次识别耗时、画面捕获与 Worker 往返延迟。
- 追踪／匹配失效的类别：具体哪侧肩、肘、腕出画或可见性低，肩线问题、面部缺失／过小／转向、角度未匹配或结果过期。只记录类别，不记录坐标或具体置信度。

点击 Download report／导出报告可下载 JSON 文件；发回该文件即可分析。面板打开时游戏仍然继续，当前报告不会逐帧刷新，点击 Refresh／刷新可获取最新数据。

最近三次报告在结束、停止、取消、错误或离开页面时保存到当前浏览器当前网址的本地存储；重新打开可在运行记录下拉框选择。运行中数值在内存累积，不逐帧写磁盘。浏览器禁止保存或空间不足时，记录和导出仍可用，但需在离开前手动下载。突然关闭浏览器或进程崩溃可能无法触发保存。

仅记录性能数值、阶段、姿势编号、识别是否有效、浏览器与粗略硬件信息。不会保存视频、图像、身体／面部关键点、表情系数、摄像头设备 ID 或完整错误消息，不会自动上传报告。

### 如何解读

先让同一位玩家在同一设备上玩一局，再比较普通题与歪头题：

- 歪头题面部耗时明显增加且刷新间隔同时变长：双模型计算值得优先排查。
- 模型调用耗时较低但界面更新或主线程长任务较高：优先检查页面与主线程工作。
- 视频帧率本身低、模型耗时不高：检查摄像头输入与设备占用。
- 仅加载／初始化耗时高、游戏内正常：检查启动阶段和网络资源加载。

身体题识别间隔设为 40ms，歪头／准备阶段为 70ms，所以“识别次/秒”本来就不同。模型耗时是同步 API 调用的墙钟时间，不是独立 GPU 时间；界面耗时测量脚本更新，不覆盖完整的布局和合成。视频帧统计基于 requestVideoFrameCallback 的呈现计数，无法提供时显示不可用。页面隐藏时间不计入可见帧率，游戏总计时仍保持原规则。未提供长任务 API 的浏览器显示“不支持”。Worker 模式的总耗时还包含画面捕获与线程往返，与旧版本同步计算总耗时不完全等价。原因统计只汇总正式题目，包含玩家正常调整动作，不能将每次不匹配都当成检测错误。这些数据用于排查相关性，不能单靠某一项判定卡顿根因。

记录设有上限：最近 4000 个识别样本、每项最近 4000 个耗时、300 个事件、600 个每秒／阶段汇总；超限会在报告标注截断。识别次数与可见时间仍累计整次运行。初始化耗时包含资源加载和模型构建，未单独测量网络传输。

技术栈：Vite + TypeScript + MediaPipe Pose / Face Landmarker + Canvas；无服务器、无数据库。

## 检查与构建

```sh
npm test
npm run build
npm run preview
```

构建产物在 `dist/`。摄像头需要 localhost/127.0.0.1 或 HTTPS，普通局域网 HTTP 地址通常不可用。

真人试玩建议：先背向或侧向屏幕，确认不会开局；转正一秒观察圆环填满；计时开始后转头不应暂停；完成姿势后确认加一分并清空旧目标；等待到零查看完成数量与设备释放；再玩一次应回到待机确认。检查在预期站位下能否稳定完成准备确认。遇到橙色头部的目标时，需要连同歪头方向一起模仿；正确手臂配错误方向的歪头应不能通过。短暂遮挡应暂停进度，长时间遮挡或明显换动作仍应重置。


## 网络与隐私

首次获取模型需要联网，Pose Lite 与 Face 模型来自 Google Storage；固定版本的 WASM 和 SDK 由本地依赖自动复制并随页面提供。npm 包与运行时 WASM 都固定为 0.10.32。当前不保证离线运行。

本 demo 不录制或主动上传摄像头画面，姿态计算在浏览器内执行，提示音在本地生成。MediaPipe 自身的度量数据行为参见官方隐私说明：https://github.com/google-ai-edge/mediapipe/blob/master/mediapipe/tasks/web/vision/README.md 。
